# MVP実装前に追加で決めること

## 1. 現時点の判定

機能要件、受け入れ要件、TDD要件、API境界、層構造は、実装へ移れる水準に達している。

ただし、以下を決めずに着手すると、録画・AI会話・シナリオ評価を実装した段階で設計変更が発生しやすい。実装開始前に「必須決定事項」を固定し、その後は原則として機能追加を止める。

---

# 2. MVPの完成範囲を二段階に分ける

主要11シチュエーション×5難易度を最初から同時に完成させると、最大55パターンの動作確認が必要になる。

そのため、実装順を次のように分ける。

## 2.1 技術的MVP

共通エンジンと、代表的な3シナリオを動作させる。

1. 初回要件ヒアリング
2. 仕様変更・追加要望
3. 納期遅延の説明

この3つは、それぞれ異なる能力を検証できる。

* 情報取得
* 交渉・スコープ管理
* 説明・謝罪・合意形成

## 2.2 個人用MVP完成版

共通エンジンを変更せず、残りのシナリオ定義を追加して主要11分類を利用可能にする。

これはスコープ削減ではなく、実装順の分離である。共通エンジンが未完成な状態で55パターンを作り始めない。

---

# 3. シナリオ定義の正式フォーマット

シナリオ定義のJSONまたはTypeScript Schemaを、最初の実装対象として固定する。

最低限、次を持たせる。

```typescript
type ScenarioDefinition = {
  id: string;
  version: number;
  title: string;
  description: string;
  enabled: boolean;

  scenes: ConcreteScene[];
  facts: ScenarioFact[];
  difficultyProfiles: DifficultyProfile[];
  compatibleClientTypeIds: string[];
  defaultFocusSkill: FocusSkill;

  successConditions: SuccessCondition[];
  evaluationRubric: EvaluationRubric;
  prohibitedAiBehaviors: string[];
};
```

## 必須の追加ルール

* IDは一度公開したら変更しない
* 表示名とIDを分ける
* ScenarioとSceneにversionを持たせる
* 過去履歴は実行時のversionを保持する
* 新しいシナリオ定義が過去の評価結果を書き換えない
* Fact IDの重複を禁止する
* 存在しないFact ID参照をSchema検証で拒否する

# 4. 難易度の数値基準

「難しい」「圧力が強い」だけではテストできないため、難易度をパラメータ化する。

```typescript
type DifficultyProfile = {
  level: 1 | 2 | 3 | 4 | 5;
  hiddenFactRatio: number;
  ambiguityLevel: number;
  contradictionCount: number;
  pressureLevel: number;
  resistanceLevel: number;
  unexpectedQuestionCount: number;
  responseWaitSeconds: number;
  timeLimitEnabled: boolean;
};
```

次の不変条件を設ける。

* レベルが上がっても曖昧さ、圧力、隠し情報が減少しない
* レベル1では人格攻撃や強い威圧を行わない
* レベル5でも差別・侮辱・罵倒は行わない
* 難易度は業務上の複雑さであり、顧客の攻撃性だけで表現しない

# 5. AIとアプリの責任境界

AIに任せる範囲を明確に固定する。

## AIが担当するもの

* 顧客としての自然な返答
* 質問分類の候補
* 結論先行、前置き、直接回答などの文章分析
* フィードバック文章の言い換え
* 部分再練習用の自然な顧客発言

## アプリが確定するもの

* 存在するシナリオ情報
* Factの状態
* 要件取得済みか
* 未確認の重要事項
* 難易度
* 顧客タイプとの互換性
* セッション状態
* フィードバック優先順位
* 改善点を一つに限定する処理
* 履歴比較
* 削除期限

AIの出力を正解データとして保存せず、必ずZod検証とDomainルールを通す。

# 6. AIの再現性とFixture

AIの応答は毎回完全には一致しない。文字列一致テストではなく、構造と禁止条件をテストする。

## 固定Fixtureに必要な種類

* 良い初回ヒアリング
* 重要要件を確認しなかった会話
* 話が散らばった回答
* 声は小さいが内容は適切な会話
* 結論が遅い納期報告
* 仕様変更へ即答してしまう会話
* 顧客の矛盾を確認できた会話
* 合意事項が存在しない会話
* 技術用語を正しく説明した会話
* 技術用語を説明しなかった会話

各Fixtureには次を持たせる。

```typescript
type EvaluationFixture = {
  transcript: ConversationTurn[];
  expectedCapturedFactIds: string[];
  expectedMissingCriticalFactIds: string[];
  expectedQuestionCategories: string[];
  expectedPrimaryImprovementCategory: string;
  forbiddenFindings: string[];
};
```

# 7. 録画とSTT用音声の分離

録画用MediaStreamを、そのままSTTへ送る設計にしない。

## 録画経路

```text
Camera＋Microphone
→ MediaRecorder
→ 5秒チャンク
→ IndexedDB
```

## 会話認識経路

```text
Microphone
→ Web Audio API
→ VAD
→ ユーザー発話区間のみ抽出
→ STT API
```

これにより、次を実現する。

* 無音時間のAPI課金を減らす
* AI顧客の音声をSTTへ混入させにくくする
* 録画失敗と文字起こし失敗を分離する
* 録画は継続しながらSTTだけ再試行できる

---

# 8. 音声出力の回り込み対策

ブラウザのスピーカーから流れるAI顧客音声を、マイクが再取得する可能性がある。

次を実装条件とする。

* AI発話中はSTT送信を停止する
* `echoCancellation`を有効にする
* TTS開始・終了時刻を記録する
* ユーザー発話との重複時間を別指標として扱う
* ヘッドホン使用を推奨表示できる
* TTS終了直後に短い猶予時間を設ける

AI発話中にユーザーが割り込む機能は、最初の技術的MVPでは対象外としてよい。割り込みを許可すると、VAD、TTS中断、発話者分離が大幅に複雑になる。

---

# 9. マイク音量の校正仕様

端末やマイクによって入力音量が異なるため、固定dBだけで「声が小さい」と判定しない。

練習前に基準文を発話して校正する。

例：

> 「本日はお時間をいただき、ありがとうございます」

校正結果から個人基準値を作り、以下を判定する。

* 通常音量
* 基準より明確に小さい
* 無音
* クリッピング

基準値はマイクまたはデバイスが変わった場合に再校正する。

# 10. 録画復旧の定義

「復旧可能」を具体化する。

## 復旧できるもの

* 保存済み録画チャンク
* 練習設定
* 練習前自己評価
* 保存済み会話ターン
* 途中までのシナリオ状態

## 復旧できない可能性があるもの

* IndexedDBへ未保存の直近チャンク
* APIへ送信中の音声
* TTS中の音声
* 未確定のAI応答

復旧候補は通常履歴と分け、「中断された練習」として表示する。

復旧後に会話を途中再開する機能は複雑なため、MVPでは次のどちらかとする。

* 保存済み内容を振り返る
* 同じ設定で新しい練習を開始する

---

# 11. 保存容量の上限

10分動画を月50回保存すると、端末容量を相当消費する可能性がある。

個人用MVPでは、録画動画の保存可能本数を**最大20本**に固定する。

* 映像解像度：720p以下
* フレームレート：24fpsまたは30fps以下
* 映像ビットレート上限
* 1録画当たりの推定最大容量
* 保存可能本数：20本
* 保存容量警告の閾値
* 30日自動削除の境界時刻

## 11.1 保存本数上限の振る舞い

* 保存済み録画が19本以下の場合、新しい録画を通常保存する
* 保存済み録画が20本ある状態で新しい録画を保存する場合、新しい録画の保存完了後に、作成日時が最も古い非お気に入り録画の自動削除を確定する
* 削除対象は動画だけでなく、その動画に紐づく録画チャンクも含む
* 練習履歴、自己評価、音声分析、会話分析、シナリオ評価、フィードバックは削除せず残す
* 履歴画面には「録画は保存上限により自動削除されました」と表示する
* 自動削除は、新しい録画の保存が完了した後に確定する
* 新しい録画の保存失敗時には既存録画を削除しない
* 復旧途中の録画は通常の20本には含めず、別枠で管理する
* 動画を手動削除しても、練習履歴や分析結果は残す

## 11.2 お気に入りの扱い

以前の「お気に入り動画は自動削除しない」という要件は、次のルールに統一する。

1. 非お気に入り録画のうち、最も古いものを優先削除する
2. 20本すべてがお気に入りの場合、新しい録画の開始を停止する
3. ユーザーに「お気に入りを解除または動画を削除してください」と表示する
4. お気に入りを無視して自動削除することはしない

これにより、保存上限を20本に固定しながら、お気に入りの意味も維持する。

## 11.3 受け入れ要件

* 保存録画数が20本を超えない
* 20本未満では既存録画が削除されない
* 21本目の保存時に、最古の非お気に入り録画が削除される
* 新規録画の保存失敗時に既存録画が削除されない
* 動画削除後も練習履歴と分析結果を確認できる
* すべてがお気に入りの場合、新規録画を開始できない
* 自動削除された履歴には削除理由が表示される
* 同じ処理が二重実行されても、複数の動画が誤って削除されない

## 11.4 TDDテスト要件

### Unit Test

* 19本では削除対象を返さない
* 20本では最古の非お気に入り録画を返す
* 作成日時が同じ場合は、録画IDなどの安定した副キーで削除対象を決定する
* お気に入り録画を削除候補から除外する
* 全20本がお気に入りの場合は`RecordingLimitReachedError`を返す
* 復旧候補を通常録画数へ含めない

### Integration Test

* 新規録画保存後、古い動画Blobと録画チャンクだけが削除される
* 練習セッション、自己評価、分析結果は削除されない
* 新規保存に失敗した場合、削除トランザクションを実行しない
* 削除途中で失敗した場合も、IndexedDBの整合性が維持される
* 同じ保存要求を再送しても、削除が一度だけ行われる

### E2E Test

1. 録画を20本保存する
2. 最古の録画と最新の録画を確認する
3. 21本目を保存する
4. 最古の非お気に入り動画が再生不可になる
5. その練習の分析結果は引き続き表示される
6. 新しい録画が履歴へ追加される
7. 保存録画数が20本のままである

## 11.5 データモデルへの追加

```typescript
type RecordingMetadata = {
  id: string;
  sessionId: string;
  createdAt: string;
  deletedAt: string | null;
  deletionReason:
    | "manual"
    | "retention_expired"
    | "recording_limit"
    | null;
  isFavorite: boolean;
  status: "recording" | "completed" | "recoverable" | "deleted";
};
```

## 11.6 正式な要件文

> 個人用MVPでは録画動画を最大20本まで端末内に保存する。新しい録画の保存によって上限を超える場合、最も古い非お気に入り録画を自動削除する。動画に紐づく練習履歴、自己評価および分析結果は保持する。20本すべてがお気に入りの場合は新しい録画を開始できない。

録画本数を固定することで、動画ビットレートや端末ごとの差に依存せず、保存容量を予測しやすくする。また、履歴と分析を残すことで、動画が自動削除されても過去比較機能を維持する。

# 12. ローカルデータのマイグレーション

IndexedDBのSchema変更に備えて、最初からDexieのversionを使用する。

```typescript
this.version(1).stores({
  practiceSessions: "id, createdAt, scenarioId",
  recordingChunks: "id, recordingId, sequence",
});
```

設計条件：

* Schema変更時に既存履歴を可能な限り保持する
* Scenario versionとDB versionを混同しない
* 移行失敗時に全データを自動削除しない
* 開発者向けにエクスポート機能を用意してもよい
* 大規模変更前にIndexedDBバックアップを取れる構造にする

---

# 13. APIコスト上限

月20〜50回、1回5〜10分を前提に、アプリ側の制限を設ける。

* 1発話の音声上限：30秒
* AI顧客の返答：原則1〜3文
* 出力上限：200〜250トークン
* 直近会話履歴：数ターン
* 古い履歴：構造化要約
* 会話分析：終了後に1回
* 自動再試行：最大2回
* 同じTurn IDの重複API実行を防止
* 月間API利用量をローカル集計する

一般公開前でも、想定外のループでAPIが連続実行されないよう、1セッション当たりの最大ターン数を決める。

---

# 14. 冪等性

録画終了、AI応答、セッション削除などは、二重クリックや再送で重複しないようにする。

対象：

* 練習開始
* 録画開始
* 発話処理
* AI応答生成
* 練習終了
* 分析開始
* 部分再練習作成
* セッション削除

`sessionId`、`turnId`、`requestId`を用いて重複処理を防ぐ。

特にAI応答APIは、同じ`userTurnId`に対して複数の顧客応答を保存しない。

---

# 15. 状態管理の単一化

Zustand、Domain Entity、IndexedDBの3か所で異なる状態を持たない。

## 正式な状態

`PracticeSession`のDomain状態を正とする。

## Zustand

画面描画に必要な一時状態と、Domain状態の参照を持つ。

## IndexedDB

Domain状態の永続化結果を持つ。

UI独自の文字列状態を追加せず、状態遷移表を一か所で定義する。

---

# 16. エラー後の再開地点

エラー別に、どこへ戻るかを固定する。

| エラー    | 戻る地点          |
| ------ | ------------- |
| カメラ拒否  | デバイス確認        |
| マイク拒否  | デバイス確認        |
| STT失敗  | 同じ発話の再送       |
| AI応答失敗 | Transcript確定後 |
| TTS失敗  | テキスト表示状態      |
| 録画保存失敗 | 会話継続または安全終了   |
| 会話分析失敗 | 結果画面の再分析待ち    |
| 容量不足   | 履歴・動画削除画面     |

「再試行」ボタンの意味がエラーごとに異ならないようにする。

---

# 17. プライバシー表示

個人用でも、将来公開時に流用できる表示を作る。

練習開始前に明示する。

* 動画は端末内に保存される
* 音声認識のため音声の一部を外部APIへ送る
* 会話生成・分析のため文字起こしを外部APIへ送る
* 動画全体は外部APIへ送らない
* 管理者や他ユーザーはデータを閲覧しない
* ブラウザデータ削除で動画が消える可能性がある

「完全非公開」ではなく、外部送信範囲を具体的に記載する。

---

# 18. 管理者実験モードの保護

個人用でも、通常画面と実験画面を分離する。

* `/admin`配下へ分離
* 本番ビルドで非表示にできるFeature Flag
* 通常履歴をFixtureとして自動利用しない
* Prompt内の秘密情報をクライアントへ返さない
* Scenario変更時は新versionを作る
* 公開中versionを直接上書きしない

Phase 0では簡易的な環境変数による有効化でもよい。

---

# 19. 画面遷移と戻る操作

ブラウザの戻るボタンを含めて仕様化する。

* 設定途中では選択状態を保持する
* 練習中の戻る操作では確認ダイアログを出す
* 自己評価前に結果画面へ直接移動できない
* 完了前にURLを直接開いても不正遷移を拒否する
* 削除済みセッションのURLでは安全な代替表示を出す
* 録画中のページ離脱では`beforeunload`警告を利用する

# 21. シナリオ作成作業の管理

主要11分類を一度に記述せず、シナリオごとに次のDefinition of Doneを設ける。

* Scenario Schemaに適合する
* Fact IDが重複していない
* 重要項目が定義されている
* 難易度1〜5の差が明確
* 対応顧客タイプが定義されている
* 成功条件が定義されている
* 禁止AI挙動が定義されている
* 最低3件の会話Fixtureがある
* 本人が一度以上通し練習した
* AIが隠し情報を早期開示しない

# 25. 忌憚のない最終評価

現時点で最大のリスクは、コード量ではなく、次の三点である。

1. **シナリオ品質**
   11分類×5難易度を作る作業は、画面実装より重い。

2. **ブラウザ音声処理**
   録画、VAD、STT、TTSを同時に動かす部分は、机上設計だけでは確定できない。

3. **AI評価の信頼性**
   AIに要件取得の最終判定を任せると、テストが不安定になる。

そのため、最初に作るべきものは管理画面でも全シナリオでもなく、次の縦断的な1本である。

```text
設定
→ デバイス確認
→ 録画
→ 一発話のSTT
→ AI顧客返答
→ TTS
→ 終了
→ 自己評価
→ 固定ルール評価
→ 履歴保存
```

この1本が動作してから、複雑な評価と残りシナリオを追加する。
